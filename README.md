# llm-agent-evals

A small tool-calling LLM agent with NDJSON streaming, model fallback, a "rescue parser" for models that print tool calls as text, per-user file memory, response caching, a daily usage counter, and an **eval harness** that replays a golden set against the HTTP endpoint and scores answers with heuristics.

Everything runs offline against a deterministic **mock provider**, so the tests and evals need no API key. Point it at any OpenAI-compatible endpoint to use a real model.

Author: Sergio Atanacio. License: MIT. The shop, products, sales and goals are entirely synthetic and generated by `src/db.ts`.

> Status: a portfolio / learning project. It has not been run in production and no claims are made about real-model quality (see [Limitations](#limitations)).

## Quick start (no API key)

Requires Node 22+ (developed and run on Node 24 / Windows 11). Node 20 is not supported: `better-sqlite3` ships no prebuilt binary for it on Windows and the install falls back to a native compile.

```bash
npm install
npm test                      # 35 tests
npm run evals                 # 32 golden cases against the mock provider, in-process server
npm run evals:compare         # prompt v1 vs v2
npm run seed                  # (optional) create data/shop.db; the server also seeds on first start
npm start                     # http://127.0.0.1:8787
```

```bash
curl -N -X POST http://127.0.0.1:8787/chat \
  -H "content-type: application/json" \
  -d '{"user":"demo","message":"Top 3 products by revenue in the last 30 days"}'
```

The response is `application/x-ndjson`, one JSON event per line:

```
{"type":"status","message":"received","user":"demo"}
{"type":"status","message":"thinking","turn":1}
{"type":"tool","name":"top_products","args":{...},"ok":true,"summary":"..."}
{"type":"text","delta":"Harbor Blend Beans 1kg l"}
...
{"type":"done","ok":true,"text":"...","tools":["top_products"],"turns":2,"model":"mock-1","fell_back":false,"cached":false,"usage_remaining":199}
```

Other endpoints: `GET /health`. Request body: `user` (`[A-Za-z0-9_-]{1,64}`), `message` (<= 2000 chars), optional `prompt_version` (`v1`|`v2`), optional `no_cache`.

Write flow example (propose, then confirm in a second message):

```bash
curl -sN -X POST localhost:8787/chat -H "content-type: application/json" -d '{"user":"demo","message":"Change the price of MUG-002 to 25.90"}'
curl -sN -X POST localhost:8787/chat -H "content-type: application/json" -d '{"user":"demo","message":"yes, confirm"}'
```

## Using a real provider

Copy `.env.example` to `.env` (git-ignored) or set environment variables:

```bash
LLM_PROVIDER=openai
LLM_BASE_URL=https://api.openai.com/v1     # or any OpenAI-compatible server (local or hosted)
LLM_API_KEY=...
LLM_MODEL=<model id>
LLM_FALLBACK_MODEL=<backup model id>        # optional
```

Then `npm start`, or `npm run evals` (the in-process server uses the same env), or `npm run evals -- --url http://host:port --token <API_TOKEN>` against an already-running server. Real calls cost money and the scores will vary run to run.

**This path is untested against a live provider.** It is covered only by unit tests with a fake `fetch` (SSE chunking, fragmented tool-call arguments, HTTP errors). Expect to adjust things the first time you try a specific vendor.

To exercise failure paths with the mock: `LLM_MODEL=mock-fail-1 LLM_FALLBACK_MODEL=mock-1` (primary always throws, fallback answers) and `LLM_MODEL=mock-text-1` (emits tool calls as text, handled by the rescue parser).

## Architecture

```
client --POST /chat--> server.ts  (validation, auth, usage limit, cache, memory load)
                          |
                       agent.ts   multi-turn loop (cap: MAX_TURNS)
                      /    |    \
        llm/(openai|mock)  rescue.ts  tools.ts --> SQLite (synthetic shop)
                          |
          NDJSON events: status | text | tool | done
```

| File | Role |
| --- | --- |
| `src/agent.ts` | Tool loop, model fallback, stream gating, rescue integration |
| `src/llm/openai.ts` | OpenAI-compatible client, SSE parsing, tool-call fragment assembly |
| `src/llm/mock.ts` | Deterministic rule-based "model" (not a language model) |
| `src/rescue.ts` | Extracts tool calls from text (tags, fenced JSON, bare JSON, `name({...})`) |
| `src/tools.ts` | 7 tools over SQLite: `sales_summary`, `top_products`, `product_lookup`, `goal_progress` (read); `propose_price_change`, `propose_goal_change`, `confirm_action` (write path) |
| `src/memory.ts` | Per-user JSON file: remembered facts + last 6 turns |
| `src/cache.ts`, `src/usage.ts` | In-memory TTL answer cache; per-user daily counter persisted to JSON |
| `evals/` | Golden set (`golden.jsonl`, 32 cases), scoring heuristics, runner and report writer |

## Design decisions

- **Propose, then confirm.** Write tools never write. They insert a row in `pending_actions` and return a summary. Only `confirm_action` applies it, and the code (not the prompt) refuses unless the *latest user message* contains an affirmative word and the pending action belongs to that user and is under 30 minutes old. A model that tries to confirm by itself gets an error. This is a keyword check, not intent understanding (see limitations).
- **Fallback only before output.** If the primary model errors or returns nothing, the next model is tried, but only if no text has been streamed yet; otherwise the user would see a duplicated or spliced answer. Once a fallback is used it stays for the rest of that request.
- **Rescue parser with a stream gate.** Some models print the tool call instead of calling it. The agent holds back the first ~24 characters of each turn; if they look like a tool call (`{`, a fence, `<tool_call>`, `name(`), the whole turn is buffered and parsed, so the raw JSON is not shown to the user. Only known tool names are accepted.
- **Cache only self-contained questions.** The key is (prompt version, model, normalized message, remembered facts). Messages that look like follow-ups ("and for May?", "yes") or arrive while an action is pending are never cached, and any confirmed write clears the cache.
- **Few dependencies.** Runtime: `better-sqlite3` only (Node's built-in `node:sqlite` needs Node 22+). Dev: `typescript`, `tsx`, `@types/*`. HTTP server, tests (`node:test`), fetch, .env loading are all built in or ~15 lines.
- **Deterministic data.** The dataset (24 products, 3 stores, ~4.5k sales lines, monthly goals for Jan-Jul 2025) comes from a seeded PRNG; "today" is fixed to 2025-06-30 (`AS_OF_DATE`) so answers are reproducible.
- **Eval isolation.** The runner uses a fresh user per case, `no_cache: true`, and (without `--url`) a temp data directory, so runs don't pollute each other or `data/`.

## Eval harness

`npm run evals [-- --prompt v2] [-- --compare v1] [-- --min-pass 0.9] [-- --url ...]`

Each golden case is a question (or a multi-turn script) with optional expectations. Per turn it checks:

| Check | Meaning |
| --- | --- |
| `answer_first` | Does not open with filler or narration ("Sure!", "Let me...", "I'll...") |
| `no_tool_leak` | No tool names, raw tool-call JSON or "system prompt" in the answer |
| `no_narration` | No "I called/used/ran...", "first, I...", "using the ... tool" |
| `format` | Non-empty, <= 700 chars, <= 8 lines, no markdown headings/bold |
| `tool_use` | Expected tools were called; `[]` means none; forbidden tools (e.g. `confirm_action` on the proposal turn) were not |
| `content` | Optional regexes the answer must / must not match |

It writes `evals/reports/report-<timestamp>.md` and `.json` (git-ignored), and exits non-zero if the pass rate is under `--min-pass`. With `--compare`, it runs both prompt versions and prints a per-check delta table and which cases flipped.

### Measured result (mock provider, this repo, one run)

| prompt | cases passed | answer_first | no_tool_leak | no_narration | format | tool_use |
| --- | --- | --- | --- | --- | --- | --- |
| v1 | 7/32 (22%) | 21% | 21% | 21% | 97% | 100% |
| v2 | 32/32 (100%) | 100% | 100% | 100% | 100% | 100% |

**Read this carefully:** the mock changes its writing style depending on whether the system prompt contains "answer first" (v2 does, v1 does not). So this table demonstrates that the harness detects and reports a style regression and that the pipeline works end to end. It says **nothing** about how v1 or v2 would behave on a real model. The same goes for the 100% on v2: the mock was written to satisfy these checks.

## Tests

`npm test` runs 35 `node:test` tests through `tsx`: rescue parser shapes, tool validation and the confirmation guard (self-confirm, wrong user, expiry, cancel), memory/usage/cache, the OpenAI client against a fake `fetch`, the agent loop (turn cap, fallback, rescue, propose/confirm), the HTTP server (NDJSON events, auth, validation, 413, cache, daily limit, memory across requests), and the scorer plus golden-set sanity.

CI (`.github/workflows/ci.yml`) runs typecheck, tests and the mock evals on Ubuntu and Windows with Node 22 and 24.

Verified locally on Windows 11 with Node 24.14: clean `npm ci`, typecheck, 35/35 tests, mock evals (default, `mock-text-1` rescue mode and `mock-fail-1` fallback mode all 32/32), and the real server queried with `curl` (read question, propose, confirm, fallback event).

**Not verified:** any live provider (no API key was used, no paid calls made); Node 20 (unsupported, see above); behavior under concurrent load.

## Limitations

- The mock is a keyword matcher, not a model. All eval numbers above come from it. Real-model behavior (especially `answer_first` and narration) needs a real run, and heuristic scoring is a proxy: regexes miss paraphrases and can flag harmless text.
- The golden set is small (32 cases), written by one person, mostly English with a few Spanish cases, and contains no real user data.
- Confirmation is a keyword regex on the last message ("ok", "yes", "confirm"...). It can misfire on messages like "no, ok let me think" and is not an authorization system. There is no real authentication either: `user` is client-supplied; `API_TOKEN` is a single shared bearer token.
- Cache is in-memory, single process, and its follow-up detection is a heuristic. Usage counting is per process-file with no locking, so running two server instances on one data dir can lose updates.
- Streaming is per turn: text produced before a tool call (narration in v1) is streamed as it arrives. If a model prints a tool call after already streaming normal text, that text cannot be unsent.
- Tool arguments get light manual validation, not full JSON-schema validation. No token accounting; "usage" means request count. No retries/backoff beyond the single fallback model.
- SQLite access is synchronous (`better-sqlite3`), fine for a demo, not tuned for load.
